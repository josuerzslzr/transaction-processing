# Transaction Processing Practice Project

## Objective

Build a production-oriented transaction-processing practice system inspired by the
architectural concerns of financial platforms. The project is a learning system, not a real
financial processor.

The planned technology areas are:

- Kotlin/JVM and Spring Boot
- AWS DynamoDB
- event-driven processing and AWS Kinesis
- Amazon EKS and Terraform
- GitHub Actions
- OpenSearch and Datadog
- distributed-system resilience patterns

Work proceeds through the approved iterations in `ROADMAP.md`. Do not introduce
functionality assigned to a later iteration.

## Domain language

A **client** is the company or platform directly consuming the transaction API, such as a PSP,
wallet provider, large merchant, or another transaction platform. It is not the end consumer.
`clientId` is the ownership and tenant identifier. A merchant may exist behind a client, but
merchant modeling is not currently a separate aggregate.

Core identifiers are:

- `clientId`: identifies the API client and scopes all transaction access.
- `transactionId`: identifies a transaction generated by this system.
- `externalReference`: required opaque business/order reference supplied by the client. It is
  case-sensitive, non-unique, preserved without trimming, and is not a lookup or
  idempotency key.
- `idempotencyKey`: client-generated UUIDv7 identifying one logical create operation. It is
  distinct from `transactionId`.
- `eventId`: UUIDv7 identifying an immutable transaction lifecycle event.
- `correlationId`: reserved for later distributed observability. It must not be used as the
  idempotency mechanism.

Use UUIDv7 for identifiers generated or accepted by this project. UUIDv7 supplies useful
approximate chronological ordering, but it is not a strict distributed sequence.

## Initial transaction model

Represent money with integer minor currency units, never `float` or `double`. The first slice
supports only EUR, so `amountMinor: 4250` represents EUR 42.50.

The create request requires:

- `externalReference`: 1-128 characters and not whitespace-only; preserve the supplied value.
- `amountMinor`: positive signed 64-bit integer.
- `currency`: `EUR`.
- `transactionType`: `PAYMENT`.
- `paymentMethod`: `BANK_TRANSFER`.

`transactionType` identifies the business operation. Iteration 2 supports only `PAYMENT`;
wallet transfers, refunds, and other transaction types remain deferred. `paymentMethod` is
payment-specific and required for `PAYMENT`. `BANK_TRANSFER` is simulated: the system does not
identify a bank, contact a provider, move money, or reconcile a real transfer.

The initial lifecycle is:

```text
CREATED -> PROCESSING -> SUCCEEDED
                      -> FAILED
```

`SUCCEEDED` and `FAILED` are terminal in the current lifecycle. Cancellation is deliberately
deferred. A future iteration may introduce cancellation commands and states such as
`CANCEL_PROCESSING`, `CANCEL_SUCCEEDED`, and `CANCEL_FAILED`, but none are part of the current
contract or model.

## Initial API boundary

The authoritative contract is `api/openapi.yaml`. It is maintained contract-first; Spring
controllers and Kotlin transport DTOs will be handwritten and checked for conformance. Do not
generate Spring server interfaces, DTOs, controllers, or a server skeleton from the contract.

The first public operations are:

- `POST /v1/transactions`: create a transaction idempotently and return its generated `transactionId`.
- `GET /v1/transactions/{transactionId}`: retrieve a transaction owned by the requesting client.

`X-Client-Id` is required on both operations and is a development identity mechanism, not
authentication. `Idempotency-Key` is additionally required on create. The client must retain
the returned `transactionId` for later retrieval. There is no external-reference lookup, list,
history, cancellation, or transition API in the first slice.

Errors use RFC 9457 `application/problem+json`. The HTTP code remains authoritative for HTTP
behavior, the numeric problem `status` matches it, and `type` identifies the stable error
category. The API does not define an additional numeric return-code catalogue.

## Architecture and persistence

Use one Gradle Kotlin DSL monorepo with a Java 21 toolchain, Kotlin 2.4.10, Spring Boot 4.1.1,
and the Spring Framework version managed by Boot (7.0.9 at the Iteration 1 baseline).

The first implementation iteration will introduce:

- `transactions-core`: pure Kotlin domain model, application use cases, ports, lifecycle rules,
  and idempotency fingerprinting; no Spring or AWS dependencies.
- `transactions-dynamodb`: DynamoDB records, strongly consistent reads, conditional transactions,
  and implementations of core persistence ports.
- `transactions-api`: Spring Boot MVC application, transport DTOs, validation, RFC 9457 handling,
  and dependency wiring.

Iteration 7 may add `transactions-processor` as an independently runnable worker using the same
core use cases and DynamoDB adapter. Internal modules build together and are not published to
a remote artifact repository.

DynamoDB is authoritative. Use a single table modeled from explicit access patterns rather
than relational normalization:

```text
Transaction
PK = CLIENT#<clientId>#TRANSACTION#<transactionId>
SK = TRANSACTION

Transaction event
PK = CLIENT#<clientId>#TRANSACTION#<transactionId>
SK = EVENT#<UTC YYYYMMDD>#<eventId>

Create-transaction idempotency
PK = CLIENT#<clientId>#IDEMPOTENCY#CREATE_TRANSACTION#<SHA256(raw idempotency key)>
SK = IDEMPOTENCY
```

Transaction state is mutable and authoritative. Events are immutable audit history; the system
does not use event sourcing. Idempotent creation atomically writes the idempotency record,
transaction state, and `TRANSACTION_CREATED` event. Later state transitions atomically update state and
append one event, guarded by expected status and numeric version.

## Explicit non-goals

Do not implement before an approved roadmap iteration requires it:

- real payment providers, bank integration, or money movement
- settlement, reconciliation, financial ledger, refunds, or chargebacks
- authentication or authorization infrastructure
- PCI or card data
- cancellation
- Kinesis or DynamoDB Streams
- OpenSearch or Datadog
- Terraform, EKS, or applied AWS infrastructure
- deployment pipelines or frontend work
- multi-region behavior or event sourcing

Prefer the smallest implementation satisfying the active iteration while preserving explicit
domain boundaries, deterministic behavior, and testability.
